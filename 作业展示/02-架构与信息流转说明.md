# 02-架构与信息流转说明

本文说明：一份工作如何从「张若彤的一个想法」变成「公共仓里的一条正式知识」，中间经过哪些节点、哪些文件、哪些校验。

---

## 一、分层架构

```
                    总工作空间（非 Git 仓库）
        ┌──────────────────┼──────────────────┐
   01-早鸟票公共仓    02-张若彤个人仓     03-王小明个人仓
   （团队中枢）        （独立工作室）        （独立工作室）
        │                  │                  │
        └────── 只能经 04-交换区 横向传递 ─────┘
                     （必须携带单据）
```

三个仓库**没有 Git 远程互连**，彼此版本历史互不包含。横向联系只有一条：公共仓 `04-交换区/`。
这条唯一通道是整个设计的支点——它让「谁在什么时候把什么交给了谁」变成可追踪的文件证据。

---

## 二、一次完整流转的十个节点

以已跑通的真实案例（`ZRT-20261029-01` / `WXM-20261029-01`）为例：

| 节点 | 位置 | 产生物 | 校验点 |
| --- | --- | --- | --- |
| ① 建单 | 张若彤 `02-任务/` | 六件式任务包 ZRT-20261029-01 | — |
| ② 发起 | 张若彤 `02-任务/05-协作记录.md` | 拟稿协同单 | — |
| ③ 投递 | 公共仓 `04-交换区/待领取-*/` | `协同单-20261029-001.md` | R1–R8 全量 **Hook 触发** |
| ④ 接单 | 王小明 `01-输入/` | 协同单副本 + 接单记录 | R1–R8 **Hook 触发** |
| ⑤ 加工 | 王小明 `02-任务/` | 六件式任务包 WXM-20261029-01 | — |
| ⑥ 产出 | 王小明 `03-生效区/` | `订单接口确认说明-20261029.md`（DOC-20261029-001） | R1–R8 **Hook 触发** |
| ⑦ 回执 | 公共仓 `04-交换区/已完成-20261029/` | `回执单-20261029-001.md` | R7 校验「回复的协同单」真实存在 |
| ⑧ 验收 | 张若彤 `03-生效区/` | `ZRT-20261029-01-验收结论.md`（VR-20261029-001） | R1–R8 **Hook 触发** |
| ⑨ 沉淀 | 公共仓 `动态知识/待审核/` → `current/` | ZS-001 | **R9 发布红线（三重条件）** |
| ⑩ 归档 | 两仓 `04-归档/` | 任务包整体迁移 | 更新公共看板 |

**关键点**：每一次交付动作都同时产生「业务文件」和「单据文件」，二者通过 YAML 字段互相锚定。单据不是形式主义——它是让「交付」这件事可被机器验证的最小载体。

## 三、交换区：唯一的横向通道

### 目录约定

```
04-交换区/
├── README.md                    # 流转规则
└── 已完成-20261029/             # 按日期归档已闭环的单据
    ├── 协同单-20261029-001.md   # 委托证据（原件）
    └── 回执单-20261029-001.md   # 交付证据（原件）
```

流转过程中可临时建立「待领取-发起方-接收方/」线程目录，闭环后整体移入「已完成-日期/」。

### 为什么交换区必须存在

没有交换区时，跨成员协作只有两种退化形态：要么直接改对方文件（无法追溯、互相踩踏），要么靠聊天工具口头传达（无法版本化、事后无法考证）。
交换区把「沟通」翻译成「带字段的文件」，从而 **让交付行为本身可校验**。

### 交换区不是自动通道

当前三仓无远程，**投递与接单靠复制文件 + 各自提交模拟**（人工操作）。真实环境应由远程Git同步。这是本作业明确标注的「已模拟」项。

## 四、三种单据与线索串联

| 单据 | 流向 | 关键 YAML 字段 | 在案例中的实例 |
| --- | --- | --- | --- |
| 协同单 | 委托方 → 受托方 | `发起人` `接收人` `任务包` `状态` | `协同单-20261029-001` |
| 回执单 | 受托方 → 委托方 | `回复的协同单` + 交付物路径 | `回执单-20261029-001` |
| 退回单 | 收到方 → 发起方 | `针对的协同单` + 退回原因 | **尚无实例**（本轮一次通过未触发） |

三者构成闭环，且程序可交叉验证：回执单/退回单指向的协同单必须真实存在（R7）。

**退回单状态：模板与规则已完备并通过结构校验，但从未在真实流程中被使用——其业务有效性未经验证。**

## 五、六件式任务包

模板位置：`02-协作契约/任务包模板/六件式任务包-模板.md`

| 件 | 文件 | 回答什么问题 |
| --- | --- | --- |
| 1 | `01-任务说明.md` | 做什么、为什么、边界在哪 |
| 2 | `02-输入清单.md` | 依赖什么资料与接口 |
| 3 | `03-执行计划.md` | 分几步、谁做、何时完成 |
| 4 | `04-产出清单.md` | 交什么、按什么标准验收 |
| 5 | `05-协作记录.md` | 与谁协同、走过哪些单据、当前状态 |
| 6 | `06-沉淀归档.md` | 哪些成果进知识区、如何归档 |

### 为什么是「六件」而不是一个文件

- **1–4 件**是给执行者看的：接手即知做什么、靠什么、怎么干、交到什么程度。
- **第 5 件**是给对账看的：单据流水集中一处，使个人进度可被汇总到公共看板（本文第六节）。
- **第 6 件**是给沉淀看的：强制在任务开始时就想清楚「产出中哪部分值得成为公共知识」，避免事后遗忘。

### 真实实例

| 任务包 | 位置 | 状态 |
| --- | --- | --- |
| `ZRT-20261029-01-早鸟票活动页面订单接口确认` | 张若彤 `04-归档/`（01–06 齐全） | 已归档 |
| `WXM-20261029-01-订单接口确认` | 王小明 `04-归档/`（01–06 齐全） | 已归档 |

任务包作为整体目录归档，六件不拆散——归档后仍可完整复原当时的工作上下文。

## 六、个人进度如何汇总到公共看板

### 当前真实做法（人工）

`00-推进管理/任务看板.md` 由人工读取两个个人仓中 `05-协作记录.md` 的单据流转情况后更新，并保留对账表：

| 对账项 | 个人仓侧证据 | 交换区侧证据 | 结论 |
| --- | --- | --- | --- |
| 协同单状态 | 张若彤 `05-协作记录`：已发出 | 交换区原件存在 | 一致 |
| 回执状态 | 张若彤 `01-输入/接收记录-20261029.md`：已接收 | 交换区回执单：已完成 | 一致 |
| 产出一致性 | 验收结论 VR-20261029-001：通过 | 回执单记载的交付物路径存在 | 一致 |
| 知识入库 | ZS-001 作者：王小明 | 审核记录：张若彤通过、已入 current | 一致 |

### 为什么这一环最容易失真、也最容易被忽略

个人仓的任务状态变化**不会自动反映到公共看板**。若忘记更新，就会出现「个人已完工、公共看板仍显示进行中」的割裂。
本作业的方法是：**把状态写在结构化的第 5 件里，让汇总至少可机械化**，但目前汇总动作本身仍是人工。

**状态：已模拟（跑通过一次完整对账），尚未自动化。**

## 七、流转中被机器拦住的三种情况

| 拦截规则 | 触发位置 | 目的 |
| --- | --- | --- |
| R8 目录合法性 | 任何提交 | 协同单不能随便躺在 `03-知识区/`，交付物不能混进 `04-交换区/` |
| R7 引用有效性 | 任何提交 | 回执不能指向不存在的协同单，任务包编号不能凭空捏造 |
| R9 发布红线 | 知识区 current / history | 未过审核的成果不能冒充正式知识 |

详细规则与实测输出见 `04-稳定性机制与测试报告.md`。
