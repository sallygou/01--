# 04-稳定性机制与测试报告

本文对应课程要求的**系统稳定性三件套**：YAML 结构化 → 脚本确定性校验 → Hook 自动触发，
并给出**四组测试的真实输出**与**失败后修正的完整过程**。

---

## 一、三件套总览

```
① 结构化：Markdown 顶部加 YAML 头
   把"人能读懂的文字"变成"机器可判定的数据"
            ↓ 为校验提供输入
② 脚本校验：validate.py 按确定规则检查
   R1–R9 九项检查，输出 行号 + 规则编号 + 修改建议
            ↓ 由 Hook 调用
③ Hook 触发：git commit 前自动执行
   通过→放行；失败→阻止，文件不进历史
            ↓
   人/AI 按建议修正 → 重新 add + commit → 再次校验（闭环）
```

三者缺一不可：**没有①，②无法判定；没有②，③无内容可拦；没有③，②只能靠人自觉执行。**

## 二、第一件：YAML 结构化

规范文件：`02-协作契约/YAML字段规范-v1.md`（唯一字段标准）

### 统一后的字段体系

| 类别 | 字段 | 约束 |
| --- | --- | --- |
| 标识 | `类型` | 7 种合法值：协同单 / 回执单 / 退回单 / 交付物 / 验收结论 / 动态知识 / 静态知识 |
| 标识 | `单据编号` / `文档编号` | 单据用 `类型-YYYYMMDD-NNN`；文档用 `前缀-YYYYMMDD-NNN` 或 `ZS-NNN` |
| 状态 | `状态` | 9 种合法值：草稿 / 已发出 / 已接收 / 进行中 / 待验收 / 已完成 / 已退回 / 已归档 / 已作废 |
| 人员 | `发起人` `接收人` `负责人` `作者` `审核人` | 必须在成员名册；且发起人 ≠ 接收人；审核人 ≠ 作者 |
| 关联 | `任务包` `来源任务包` `关联文件` `回复的协同单` `针对的协同单` | 必须指向真实存在的对象 |
| 时间 | `创建日期` `更新时间` | `YYYY-MM-DD` 格式 |
| 审核 | `审核人` `审核日期` `审核结论` | 进入 current / history 前必填 |

### 结构化的真正收益

改造前，`回执人` `回执日期` 这类字段名各自为政；改造后统一为 `发起人 + 接收人`、`创建日期 + 更新时间`。
字段名统一后，**程序才能用一个字典校验所有单据**——这是脚本化的前提。

> 边界：**业务正确性不属于结构化范围**。脚本只判定"字段是否合规"，不判定"接口设计是否正确"。

## 三、第二件：脚本校验

脚本：`88-工具箱/validate.py`（567 行，**零第三方依赖**——本机无 PyYAML 且按要求不安装依赖，脚本内置轻量 YAML 解析）

### 九项检查

| 编号 | 检查项 | 典型触发场景 |
| --- | --- | --- |
| R1 | YAML 格式合法 | 分隔符缺失、缩进混乱、重复字段 |
| R2 | 必填字段缺失（含日期格式） | 忘写 `发起人`、日期写成 `2026/10/29` |
| R3 | 类型合法、编号前缀与类型一致 | `类型: 接口确认` 这类自造值 |
| R4 | 状态取值合法、编号格式合法 | `状态: 搞定了` |
| R5 | 编号重复 | 两份不同单据用了同一编号 |
| R6 | 人员在成员名册、发起≠接收 | 写了名册外的人；自己发给自己 |
| R7 | 关联任务/文件是否存在、回执指向的协同单是否存在 | 引用了已删除的文件 |
| R8 | 文件所在目录符合协作规则 | 协同单落到知识区 |
| R9 | 正式知识区发布红线 | 未审核成果进 current |

模板文件（`*-模板.md`）只校验 YAML 格式与类型，占位值不参与必填判定。

### 执行方式

```bash
python 88-工具箱/validate.py 文件1.md 文件2.md   # 指定文件
python 88-工具箱/validate.py --all               # 三仓全量
printf '%s\n' "文件.md" | python 88-工具箱/validate.py --stdin   # Hook 方式（兼容中文/空格路径）
```

退出码：`0` 无错误，`1` 有错误。

## 四、第三件：Hook 触发

源码：`88-工具箱/pre-commit`（77 行，受 Git 跟踪便于分发）
安装位置：三个仓库的 `.git/hooks/pre-commit`（均为 `-rwxr-xr-x 3232 bytes`）

### 触发条件与行为

| 条件 | 行为 |
| --- | --- |
| 暂存区含 `.md` 文件 | 触发校验 |
| 暂存区无 `.md` | 直接放行，不打扰 |
| 校验全通过 | 放行提交，退出码 0 |
| 校验有错误 | **阻止提交**，退出码 1；文件留在暂存区，不删除、不覆盖、不自动修改 |
| 只有警告 | 放行（如"待审核区却标记通过"） |

### Hook 定位机制

个人仓也能自动找到公共仓的校验脚本：Hook 从自身路径向上回溯定位公共仓根目录，因此一份脚本服务三个仓库。

### 排除了两个真实缺陷（并非"写个文件就算完成"）

| 缺陷 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 中文路径静默失效 | 含中文名的单据被**无条件放行**，毫无提示 | Git 默认对中文文件名做八进制转义（`core.quotepath`），Hook 中 `for` 循环拼出的路径带引号而失效 | 改用 `git -c core.quotepath=false` + 标准输入传文件列表 |
| 管道输入被覆盖 | Hook 报告"通过"却什么都没检查 | Hook 中的 `< /dev/null` 覆盖了 `printf \| python` 的管道，文件列表为空 | 移除该重定向 |

两个缺陷的共同教训：**Hook 静默失效比不写 Hook 更危险**，因为它制造"已经验证过"的错觉。
排查方法是先用最小探针确认"Git 确实会执行 hook"，再逐步比对实际处理的文件数。

## 六、失败后的修正过程（闭环演示）

以测试 D 为例，"AI 辅助修正 → 重新校验"的真实过程：

```
① 把文件从 current/ 移出，进入待审核/
   mv "03-知识区/动态知识/current/TEST-ZS-800-未审核.md" "03-知识区/动态知识/待审核/TEST-ZS-800.md"

② 补全审核字段（AI 辅助修正）
   已补全 审核人：张若彤 / 审核日期：2026-10-29 / 审核结论：通过

③ 在公共仓登记审核记录
   00-推进管理/审核记录-2026-10-29.md 追加一行

④ 重新提交
[警告] .../待审核/TEST-ZS-800.md
  [WARN] .../TEST-ZS-800.md:8 [R9] 位于待审核区却标记为审核通过
        修改建议：若已完成审核，移入 `current/` 正式发布
--------------------------------------------------------------------
通过 0 个；跳过 1 个；警告 1 条；错误 0 条
[协作校验] 全部通过，允许提交。

[main 91862e4] 修正演示：TEST-ZS-800 补审核信息后移入待审核区
>>> 退出码=0
```

**修正闭环成立**：3 条 ERROR 全部消除、提交放行；剩下的是 **WARN**（提醒"既然已通过就该移入 current"），属于合理提示而非错误。

> 注意：测试过程中若把 B/C 的残留文件一并 `git add -A`，Hook 仍会拦住它们——这正说明 Hook 校验的是**本次暂存的全部文件**，而不是"挑一个检查"。

## 七、三条必须讲清楚的边界

### 1. 结构校验 ≠ 业务正确

脚本能判断"字段有没有、格式对不对、引用存不存在"，**判断不了**：

- 接口字段设计是否合理
- 退回理由是否站得住脚
- 职责划分是否公平
- 20 QPS 是否真的够用

这些必须由人或 AI 基于上下文判断，脚本不越界。

### 2. Hook ≠ 权限控制

Hook 只在本机 `git commit` 时生效：

- `git commit --no-verify` 可直接绕过
- 用文件系统直接改文件、绕过 Git 提交，Hook 完全不知道
- 因此 **AGENTS.md 明确禁止 Agent 擅自使用 `--no-verify`**，并要求绕过时必须留痕

真正的权限隔离要靠 CI + 受保护分支（见 06 号文档）。

### 3. AI 修正 ≠ 免审核

AI 提出的修正建议存在验证不充分的风险，更极端的情况是：为了消除报错而去修改规则本身。
因此 AGENTS.md 规定：**不得自行修改 `validate.py` 或 `YAML字段规范-v1.md` 来"让错误消失"**，确属规则问题应先提人工裁决。
