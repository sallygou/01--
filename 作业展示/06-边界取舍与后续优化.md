# 06-边界取舍与后续优化

本系统的设计原则是：**第一版优先保证流程稳定，再逐步扩展**。
本文明确七条边界，每条都说明"为什么不做"以及"如果将来要做，该怎么补"。

---

## 一、收件箱不等于真正的权限隔离

**现状**：`01-输入/` 看起来像"只有我能收"的收件箱，`04-交换区/` 看起来像"大家都可写"的公共区。
但 Git 不做目录级权限控制——在本机上，**任何人或 Agent 都可以直接编辑他人个人仓的文件**，Hook 完全感知不到这类修改。

**为什么不在第一版解决**：真正的隔离需要服务端能力（分支保护、CODEOWNERS、受保护目录），单机模拟环境加不上。硬要做只能写更复杂的脚本，反而增加故障面。

**当前的补偿手段**：
- 规则层：三份 AGENTS.md + 协作契约明确"不得直接修改他人文件"；
- 程序层：R8 校验文件落位是否合规，R6 校验人员归属；
- 留痕层：Git 历史使越权修改事后可追溯（但不预防）。

**后续怎么补**：GitHub Actions + 受保护分支（PR 必须 CI 绿 + 至少一人 review），配合 `CODEOWNERS` 指定各目录负责人。

---

## 二、Git 不能完全替代即时通讯

**现状**：所有沟通都被压缩成文件与单据。协同单代替了"在吗？"，回执单代替了"做完了"。

**为什么不继续强化**：**异步、留痕**是优点，但**延迟**是硬伤。真实场景中的快速澄清、临时决策、冲突调解，走文件流转要多花几个数量级的时间；而且"待裁决事项"目前只躺在表格里，没人会主动去看。

**当前的遗留**：VR-20261029-001 里的两笔待裁决事项（幂等键归属、20 QPS 上限）至今没有跟进机制。

**后续怎么补**：
- Git 负责"结论留痕"，IM 负责"过程讨论"，二者分工而非互相替代；
- 约定"讨论在 IM、结论回落到文件"，避免重复建设；
- 待裁决事项应有独立登记 + 到期提醒（可先用简单的每日扫读任务实现）。

---

## 三、保密资料不应直接进入公共仓

**现状**：本作业无涉密内容，业务数据均为教学模拟。

**边界**：一旦有真实密钥、客户数据、未公开方案，**不应出现在公共仓任何分支的历史中**——Git 的删除不会真正清除历史。

**当前做法**：涉密字段不写入 YAML，涉密文档不放进三仓目录；需要引用时用占位符 + 外部安全存储。

**后续怎么补**：若用到，应建 `.gitignore` 排除清单、使用环境变量或密钥管理，并在 CI 中加敏感信息扫描。

---

## 四、脚本只验证明确规则，不负责业务判断

**现状**：R1–R9 全部是**确定性判定**——字段有无、格式对错、引用存在与否、目录是否合规。

**为什么不扩展**：业务判断（接口设计是否合理、退回是否有理、优先级是否合适）需要上下文与价值判断，写成规则会变成一堆脆性的硬编码条件，**误报和漏报都会伤害团队对机制的信任**。

**边界声明**：脚本通过 ≠ 内容正确。通过校验的 DOC-20261029-001 依然可能是一份糟糕的接口设计——这是设计上允许的风险，由审核人承担。

**后续怎么补**：结构校验交给脚本，**业务正确性交给R9式的"人类可见留痕"**（审核人签字 + 审核记录），二者分离，互不冒充。

---

## 五、未审核成果不能直接进入正式知识区

**现状**：已由 R9 程序强制（三重条件：审核人在名册且 ≠ 作者、审核结论为通过、审核记录可查）。

**为什么用三重而不是一重**：只检查文件字段的话，创作者可以自己在 YAML 里写"审核人：张三、结论：通过"蒙混过关。要求**同时在公共仓审核记录里能查到同一编号**，才构成有效闭环。

**残余风险**：审核记录本身可以被伪造，且它的真实性不受程序保护——这一环终究要落到人。

**后续怎么补**：审核记录文件同样受 Hook 保护；理想情况下用 CI 要求 PR 必须由**非作者的另一位成员** approve 才能合入 `current/`。

---

## 六、不必让每个 Agent 读取所有文件

**现状**：AGENTS.md 明确要求 Agent"只在本仓内工作"，但没有技术手段限制读取范围。

**为什么不追求全量读取**：上下文越长，Agent 越容易混淆主次、引用过期内容、误改不该改的文件。按角色限定范围既是**效率优化**也是**安全边界**。

**当前做法**：靠每个目录的 README 提供"就近可知的信息"，让 Agent 不必读取全仓也能理解该目录用途。

**后续怎么补**：为每个任务包生成上下文清单（明确列出"本次需要读的 5 个文件"），而不是让 Agent 自行探索。

### Hook 的两个集中化局限（本次实测发现）

临时克隆测试暴露了两个真实问题：

1. **`.git/hooks` 不随 Git 传播**——克隆得到的新副本**没有 Hook**（本次需手工 `cp` 安装）。新成员若不安装，整套机制对他完全无效。
2. **仓库级 Git 身份不随克隆传播**——临时克隆的首次提交以 `fatal: unable to auto-detect email address`（退出码 128）告终，需重新配置身份。

这两点是本地 Hook 的天然天花板，也是为什么**必须用 GitHub Actions + 受保护分支**做集中校验：把规则从"每台机器各自安装"变成" PR 必经之路"，成员才无法绕过。

### 建议的演进顺序

```
第一阶段（已完成）：结构 → 脚本 → Hook，流程能跑通并有通过/失败证据
第二阶段：补退回单实战 + current→history 替换演练，验证异常分支
第三阶段：建立三本索引与双向引用（可脚本自动生成）
第四阶段：接远程 + Actions + 受保护分支，把本地 Hook 升级为集中校验
第五阶段：看板自动汇总 + 到期提醒 + Agent 上下文清单
```
