# 05-关键设计点总结

围绕老师讲解的完整系统，总结 14 个关键设计点。每个点回答五个问题：
**解决什么问题 / 为什么这样设计 / 如何与其他模块配合 / 如何保证稳定运行 / 当前是否实现**。

状态标记：`已实现（已验证）` · `已模拟` · `仅有规则设计` · `尚未实现`

---

## 1. 公共 Git 仓与个人 Git 仓的设计

- **解决什么问题**：多人（或多 Agent）并行工作时，试错过程互相污染、共识内容无法沉淀、个人半成品误入公共资产。
- **为什么这样设计**：公共仓只收"已经确认的东西"，个人仓放"正在试的东西"。三个仓库**各自独立的 `.git`** 是关键——它不是形式，而是让"隔离"在版本层面真实成立：任何人的混乱提交都进不了别人的历史。
- **如何配合**：个人仓 →（交换区）→ 公共仓 →（知识区）→ 被所有人复用；反向的个人仓从中汲取输入。
- **如何保证稳定**：各有独立的 Git 历史；AGENTS.md 与协作契约写明边界；脚本 R8 控制文件该落在哪个仓哪个目录。
- **当前状态**：`已实现（已验证）`。三仓各自的 git-dir 指向自身（公共仓 31 文件、张若彤 16、王小明 17），最外层 `fatal: not a git repository`。

## 2. 个人工作台与公共工作台的职责

- **解决什么问题**：分不清"团队的事"和"我的事"，导致公共仓变成杂物间、个人仓变成孤岛。
- **为什么这样设计**：公共工作台（`00-推进管理/`、`03-知识区/`、`04-交换区/`）回答"整体走到哪了"；个人工作台（`01-输入/`~`09-日志/`）回答"我的活干到哪了"。**公共仓不承载在制品，是这条分界线最实用的判据。**
- **如何配合**：个人仓第 5 件（协作记录）是两者的数据接口；公共看板是汇总结果的展示面。
- **如何保证稳定**：职责写入三份 AGENTS.md 与各目录 README；个人产出进入公共知识区必须过 R9。
- **当前状态**：`已实现`。职责划分清晰，逐项对照见 `01-工作区设计说明.md`。

## 3. 空间边界、读写权限与 Agent 工作范围

- **解决什么问题**：Agent 默认"能读能写所有文件"，容易越权修改他人成果。
- **为什么这样设计**：把权限写成**目录规则**而非口头约定——`04-交换区/` 是唯一允许跨成员写入的区域，知识区只进审核过的东西。AGENTS.md 是给 Agent 看的"操作手册"，它把抽象的权限翻译成具体的目录清单。
- **如何配合**：与成员名册配合判定"谁是谁"，与 YAML 字段配合判定"这是谁的文件"。
- **如何保证稳定**：规则层（契约 + AGENTS）+ 程序层（R8 目录校验、R6 成员校验）；AGENTS.md 明令禁止 Agent 用 `--no-verify` 绕过。
- **当前状态**：`已实现（部分）`——规则与字段校验已程序化；**Git 本身不做目录级权限隔离，物理上仍可直接编辑他人文件**，这是必须用 CI + Code Review 兜底的部分。

## 4. 公共交换区与三种单据的流转

- **解决什么问题**：跨成员交付靠口头传达，事后无法考证"到底交付了没、什么时候交付的"。
- **为什么这样设计**：把沟通翻译成**文件**。三种单据覆盖完整生命周期：协同单（委托）→ 回执单（交付）→ 退回单（拒收）。每一步都留下带编号、带时间戳、带双方姓名的文件。
- **如何配合**：单据编号就是索引键；回执单 `回复的协同单` 字段把两次动作串成链条；交付物路径让回执指向具体文件。
- **如何保证稳定**：R7 校验引用真实存在，R4 校验编号格式，R8 校验单据只能在交换区或个人仓 `01-输入/`。
- **当前状态**：`已模拟`。协同单与回执单已真实跑通一次；**退回单模板齐备但从未实战**；投递动作靠复制文件模拟（无远程）。

## 5. Markdown 与 YAML 结构化机制

- **解决什么问题**：Markdown 对人友好、对机器不友好。只要文件是纯文本，任何"自动校验"都无从下手。
- **为什么这样设计**：在 Markdown 顶部加 YAML 头，**保留人的可读性，增加机器的可判定性**——这是成本最低的结构化改造，无需换工具、无需数据库。
- **如何配合**：YAML 字段规范是校验脚本的唯一输入；编号体系让跨文件引用成为可能。
- **如何保证稳定**：R1 校验 YAML 本身合法（含重复字段检测）；字段名必须严格取自规范 v1（`回执人` 这类自造名已统一为 `发起人/接收人`）。
- **当前状态**：`已实现（已验证）`。9 个受控文件全部通过；**仍有 53 个文件无 YAML 头、不受结构校验保护**。

## 6. 六件式任务包及个人执行过程

- **解决什么问题**：任务信息散落在对话与各处文件中，接手的人不知道前因后果，交接全靠解释。
- **为什么这样设计**：六件各自回答一个不可省略的问题——**做什么（1）/ 靠什么（2）/ 怎么做（3）/ 交什么（4）/ 跟谁协同（5）/ 沉淀到哪（6）**。前四件服务执行，第五件服务对账，第六件服务沉淀。任务包作为一个**目录整体**流转与归档，上下文不散失。
- **如何配合**：协同单的 `任务包` 字段指向它；第 5 件是公共看板的数据来源；第 6 件驱动知识沉淀。
- **如何保证稳定**：R7 校验任务包编号真实存在；归档时整体 `git mv`，六件不拆散。
- **当前状态**：`已实现（已产生实例）`。两个任务包均以完整六件归档于各自 `04-归档/`。

## 7. 个人进度与公共看板的对账同步

- **解决什么问题**：个人说"做完了"，公共侧不知道；或相反——两边状态不一致，管理层看到的永远是过时的图。
- **为什么这样设计**：状态只认**单据证据**不认口头声明。看板每一行都要求标注"关联单据"，对账单要求列出"个人仓侧证据 vs 交换区侧证据"两列，**不一致就必须查出哪一列是假的**。
- **如何配合**：数据来源是个人仓第 5 件；真实性由交换区单据原件佐证。
- **如何保证稳定**：目前靠**人工更新 + 人工核对**（公共仓提交 `199ac31` 完成过一次四项对账）。理想状态是由脚本汇总 `05-协作记录.md` 自动生成。
- **当前状态**：`已模拟`。看板已启用并跑通一次对账；**更新仍为手工，自动化未实现**。

## 8. 知识区的静态知识与动态知识

- **解决什么问题**：把"稳定规范"和"会变的成果"混在一起，前者被频繁修改、后者过期了没人知道。
- **为什么这样设计**：**静态知识**（规范、背景资料）写完基本不动，可以放心引用；**动态知识**（接口清单、当前指标）会随时间变化，必须带上版本语义。区分二者，读者才知道"这条能信多久"。
- **如何配合**：动态知识的产出来源是任务包第 6 件；静态知识往往是协作契约的补充背景。
- **如何保证稳定**：不同的目录、不同的落位规则（R8）；动态知识进入正式区还要过 R9。
- **当前状态**：`已实现（结构）`。两类目录齐备，动态知识有真实条目 ZS-001；**静态知识目前只有说明文件，尚无正式条目**。

## 9. 个人成果的审核与知识沉淀

- **解决什么问题**：个人写得再好也可能有偏差，未经审阅就把个人半成品当团队真理，错误会被反复放大。
- **为什么这样设计**：强制增设 **`待审核/` 暂存区**——没有暂存区，"未经审核不得入库"就没有落点。审核留痕要求：前必须通过协作流转或他人确认，并在审核记录中登记。
- **如何配合**：与交换区的单据闭环联动；审核人必须 ≠ 作者，从制度上排除自我审核。
- **如何保证稳定**：**R9 三重校验**：有审核人且在名册且 ≠ 作者、审核结论为"通过"、在 `00-推进管理/审核记录-*.md` 中能查到该编号。三者缺一不可，防止只改文件字段就蒙混过关。
- **当前状态**：`已实现（已验证）`。ZS-001 走完全流程，且"审核（`8cdf307`）"与"入库（`d99915b`）"在 Git 历史中分离为两笔提交，可复核先后顺序。

## 10. current 与 history 的版本管理

- **解决什么问题**：知识被更新后，旧版要么被覆盖消失（无法追溯变化），要么四处堆积（不知道哪份有效）。
- **为什么这样设计**：`current/` **每类只保留当前有效版本**，`history/` 保存被替换的旧版本。读者永远先看 current——这是"默认正确性"的设计；需要比对时再查 history。
- **如何配合**：更新顺序必须是"新版本进 current → 旧版本迁入 history"，且审核在前。
- **如何保证稳定**：落到 `current/` 与 `history/` 的都得过 R9；同一个「current → history」替换动作最好是单独一次提交，便于复盘。
- **当前状态**：`仅有规则设计 + 结构齐备`。**尚未发生过版本替换**（ZS-001 只有一版），`history/` 仍为空，此流程未被验证。

## 11. 三本索引与双向引用

- **解决什么问题**：内容多了以后，人不知道团队已有什么——重复造轮子，或引用了过期版本。
- **为什么这样设计**：三本索引（**单据索引 / 任务包索引 / 知识索引**）从三个维度给出全局目录；**双向引用**让任何一份文件都能顺藤摸瓜：单据 ↔ 任务包 ↔ 知识条目 互相标注编号与路径。单靠单向引用，找到上游就找不到下游。
- **如何配合**：单据编号是天然主键；索引本身可由脚本扫描 YAML 头自动生成（这也是结构化带来的附加红利）。
- **如何保证稳定**：一旦启用，索引的生成应纳入脚本，并加入 Hook 或 CI 保证与实际内容同步。
- **当前状态**：`仅有规则设计`。`03-知识区/索引-预留.md` 记录了约定，**尚无索引实体、无引用格式，未启用**。

## 12. Skills、提示词库与共享工具箱

- **解决什么问题**：每个人都在写给 Agent 的提示词和外挂脚本，重复劳动且质量参差。
- **为什么这样设计**：沉淀公共资源到两处——**`05-提示词库/`** 收藏经过验证的提示词模板（要求标注用途、适用模型/场景、验证情况）；**`88-工具箱/`** 收藏共享脚本。区分"提示词"与"脚本"意义在于：前者近似"软经验"，必须标注适用场景与验证状态；后者是"可执行的确定性资产"，需要版本管理与同行审查。
- **如何配合**：提示词用于提高 Agent 行为的一致性；工具箱脚本直接服务于 Hook 与校验，是整个稳定性机制的执行载体。
- **如何保证稳定**：工具箱里的脚本本身受 Git 跟踪、可被他人审阅；提示词要求标注"适用模型"与"验证状态"，避免沉淀未经验证的空谈。
- **当前状态**：**工具箱 `已实现`**（validate.py + pre-commit 已在用）；**提示词库 `仅有规则设计`**（只有 README，无正式提示词条目）；**Skills 目录 `尚未实现`**（本次未涉及 Agent 技能包具体建设）。

## 13. Hook、自动通知与程序校验

- **解决什么问题**：规则写在文档里等于没写——人会忘，Agent 会忽略。
- **为什么这样设计**：把校验**前置到提交动作**。pre-commit 的代价最小、反馈最快：错误在提交那一刻就被挡住，而不是三周后清理数据时才发现。这就是三件套的收口环节。
- **如何配合**：YAML 提供输入 → 脚本提供判定 → Hook 提供执行时机。三者缺一不可。Hook 失败只阻止、**不修改任何文件**，由人或 AI 修正后重跑，形成闭环。
- **如何保证稳定**：失败输出**文件名 + 行号 + 规则编号 + 修改建议**；浏览器脚本时应当**先验证 Git 确实会执行 Hook**（本次就通过最小探针发现两个静默失效缺陷）。
- **当前状态**：`已实现（已验证）`。四组测试全部真实通过/阻止；个人仓抽查也已确认 Hook 生效。**自动通知 `尚未实现`**（无 IM/邮件/Webhook）。

## 14. 系统边界与取舍

- **解决什么问题**：追求"大而全"的自动化，往往在半路上崩掉——越复杂的机制越容易出隐性故障。
- **为什么这样设计**：本系统明确**先保证流程稳定，再逐步扩展**。凡是涉及人的决策（业务对错、退回是否有理、优先级），都不试图用脚本替代；凡是可确定性判定的（字段、格式、引用、目录），才交给机器。
- **如何配合**：这条取舍原则反向约束了第 5、9、13 点的边界——脚本只管结构，人的审核守住内容。
- **如何保证稳定**：每引入一个机制，都要求"可解释、可复核、失败时不破坏数据"。Hook 只阻止不修改，就是这个原则的产物。
- **当前状态**：`已实现（设计原则）`。具体边界清单与残余风险见 `06-边界取舍与后续优化.md`。
