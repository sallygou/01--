## 二、公共仓 / 个人仓 / 公共工作台 / 个人工作台的关系

这四个概念常被混淆，本作业的分层如下：

```
        总工作空间：ai多人协同工作台   ← 本身不是 Git 仓库
        ┌────────────────────┼────────────────────┐
  01-早鸟票公共仓            02-张若彤个人仓         03-王小明个人仓
  （团队中枢 Git 仓）        （个人 Git 仓）         （个人 Git 仓）
        │                        │                      │
        │  ┌────────────────────┴────────────────────┐ │
        └──┤  横向联系唯一通道：04-交换区（须带单据）  ├─┘
           └─────────────────────────────────────────┘
```

| 概念 | 是什么 | 在哪个仓 | 回答什么问题 |
| --- | --- | --- | --- |
| **公共仓** | 版本管理单元：一个独立 Git 仓库 | `01-早鸟票公共仓` | 团队共识存在哪、版本历史归谁 |
| **个人仓** | 版本管理单元：每人一个独立 Git 仓库 | 各自的 GitHub 仓库（`02--` / `03--`） | 我的试错如何不被别人污染 |
| **公共工作台** | 公共仓内的推进中枢 | `00-推进管理/` `03-知识区/` `04-交换区/` | 团队走到哪了、沉淀了什么 |
| **个人工作台** | 个人仓内的五个执行目录 | `01-输入/` ~ `09-日志/` | 我的活干到哪了 |

**一句话**：公共仓/个人仓是「容器」，工作台是「里面的流程面」。公共仓不承载任何人的在制品——这是最实用的判据。

## 五、稳定性三件套：YAML + 脚本 + Hook

```
① YAML 结构化         → 把「人能读的文字」变成「机器可判定的数据」
   （02-协作契约/YAML字段规范-v1.md）
        ↓ 提供输入
② 脚本确定性校验      → validate.py 九项检查 R1–R9，输出行号+规则号+修改建议
   （88-工具箱/validate.py，零第三方依赖）
        ↓ 被自动调用
③ Hook 触发           → git commit 前执行；通过放行，失败只阻止、不修改文件
   （88-工具箱/pre-commit，安装到三仓 .git/hooks/）
        ↓
   人/AI 按建议修正 → 重新 add + commit → 再次校验（闭环）
```

### 九项检查 R1–R9

| 编号 | 检查项 | 编号 | 检查项 |
| --- | --- | --- | --- |
| R1 | YAML 格式合法（含重复字段） | R6 | 人员在成员名册、发起 ≠ 接收 |
| R2 | 必填字段缺失、日期格式 | R7 | 关联任务/文件真实存在、回执指向的协同单存在 |
| R3 | 类型合法、编号前缀一致 | R8 | 文件所在目录符合协作规则 |
| R4 | 状态取值合法、编号格式合法 | R9 | **正式知识区发布红线**（审核人+结论+记录三重） |
| R5 | 编号重复 | | |

### 本地复现命令

```bash
python 88-工具箱/validate.py --all                 # 三仓全量校验
cp 88-工具箱/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

当前全量结果：**通过 9 个；跳过 61 个（无 YAML 头的说明文档与任务包六件）；错误 0 条**。

### 三条边界（务必理解）

1. **结构校验 ≠ 业务正确**：脚本只判「字段有无、格式对错、引用存在与否」，不判「接口设计是否合理」。
2. **Hook ≠ 权限控制**：`git commit --no-verify` 可绕过，文件系统直改更拦不住；真正隔离需 CI + 受保护分支。
3. **AI 修正 ≠ 免审核**：AGENTS.md 禁止 Agent 自行修改 `validate.py` 或字段规范来「让错误消失」。

## 六、知识区：静态 / 动态、current / history、三本索引与双向引用

```
03-知识区/
├── 静态知识/          稳定规范，写完基本不动   → 目前仅说明文件
├── 动态知识/          会变的成果归集
│   ├── 待审核/        暂存区：未经审核的成果先到这里
│   ├── current/       当前有效版本（唯一正式条目：ZS-001）
│   └── history/       被替换的旧版本 → 目前为空
└── 索引-预留.md       三本索引 + 双向引用的约定
```

- **静态 vs 动态**：读者据此判断「这条能信多久」。静态是可长期引用的规范；动态需看版本。
- **待审核 → current**：`待审核/` 是「未经审核不得入库」的落点；没有暂存区，规则就没有执行位置。
- **current / history**：新版本进 current 时旧版本迁入 history，读者永远先看 current。
- **三本索引 + 双向引用**：单据索引 / 任务包索引 / 知识索引，让「单据 ↔ 任务包 ↔ 知识条目」互相标注编号，可顺藤摸瓜找到上下游。**状态：仅有规则设计（[`索引-预留.md`](03-知识区/索引-预留.md)），未启用实体。**
